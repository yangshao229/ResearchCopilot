# 开源论文阅读产品拆解协议

## 目的

ResearchCopilot 的重点是帮助用户真正读懂科研论文。任何新功能都不能只凭开发者直觉设计，必须先检查成熟开源项目如何处理相同问题，再结合本项目的本地优先、证据优先和人工确认原则作出取舍。

## 强制门槛

每一个新功能进入编码前，必须完成一份位于 `docs/research/` 的拆解记录。没有拆解记录，不开始功能实现。

拆解记录至少包含：

1. **用户问题**：功能解决读论文流程中的哪个具体困难。
2. **参考项目**：至少三个相关开源项目，优先选择维护活跃、使用者较多或有研究论文支撑的项目。
3. **一手资料**：只把项目官方仓库、官方文档、论文和源代码作为核心证据；搜索摘要和第三方介绍只能用于发现项目。
4. **流程拆解**：分别记录交互流程、数据结构、检索或模型流程、引用方式、隐私边界和失败处理。
5. **取舍表**：明确哪些设计直接借鉴，哪些需要按本项目调整，哪些明确拒绝，并说明原因。
6. **许可证检查**：借鉴思想与复制代码必须分开。若需要引入代码或依赖，先核对许可证、运行成本和跨平台影响。
7. **验收标准**：在写代码前定义可观察、可测试的完成条件，并至少包含一个失败场景。
8. **架构影响**：说明功能复用哪些既有核心对象和流水线、需要增加哪些字段、会影响哪些已有流程。若必须新增核心抽象，必须解释现有模型为什么无法承载。
9. **兼容性矩阵**：至少检查当前论文/跨论文、原文/译文、不同会话、本地/云端以及 macOS/Windows 中与该功能有关的组合，避免只验证一条理想路径。

## 固定步骤

```text
提出新功能
  ↓
查找和筛选开源项目
  ↓
阅读官方资料与关键实现
  ↓
写拆解记录和取舍表
  ↓
完成架构影响与兼容性检查
  ↓
更新产品蓝图/里程碑
  ↓
实现最小版本
  ↓
自动测试 + 真实论文验收
  ↓
记录结果和后续知识点
```

## 拆解模板

每份报告使用以下结构：

```markdown
# 功能名称：开源产品拆解

## 用户问题
## 参考项目与一手资料
## 各项目的成熟做法
## 对 ResearchCopilot 的取舍
## 数据与隐私边界
## 实现顺序
## 验收标准
## 暂不实现的内容
```

## 适用范围

该规则适用于新的用户能力、检索策略、解析方式、笔记流程、跨论文工作流和模型能力。单纯修复已经定义行为的缺陷、补测试、改文案或安全修补不要求重新完成一整轮拆解，但应引用最初定义该行为的拆解记录。

## 简洁性约束

- 新功能必须优先接入统一的论文、内容块、阅读上下文、证据、阅读记录和知识产物模型。
- 不得仅因为界面上新增一个按钮，就建立新的独立存储格式、会话体系或模型调用链。
- 同一种事实只允许一个权威来源。例如原文页码属于内容块和原文锚点，翻译、回答和笔记只引用它，不各自复制一套不可同步的页码状态。
- 如果一次改动同时改变解析、检索、生成和笔记，应拆成可独立验证的内部步骤，但对用户仍呈现同一条阅读流程。

## 记录要求

- 报告必须留下可访问的来源链接和检索日期。
- 每个里程碑的学习地图要链接对应拆解报告。
- 如果后续证据推翻原取舍，先更新报告和蓝图，再修改实现。
- 不以“其他项目有这个按钮”为采用理由；必须说明它如何改善论文阅读效果。
