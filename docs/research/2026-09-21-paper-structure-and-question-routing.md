# 论文结构与问题路由：开源产品拆解

检索日期：2026-09-21

## 用户问题

当前系统把“全文有多少章节”“有哪些大标题和小标题”等全文结构问题当成普通 RAG 问题，只检索最相似的少量片段。局部证据无法证明全文结构，最终只能安全拒答。与此同时，每篇论文需要独立的问题、阅读路线和会话，不能把不同论文的内容或提问隐式混合。

## 参考项目与一手资料

1. [Docling](https://github.com/docling-project/docling)：结构化文档表示、标题层级、阅读顺序、表格/图片和页面坐标。
2. [PaperQA2](https://github.com/Future-House/paper-qa)：面向科研文献的检索、证据收集、重评分和带引用回答。
3. [Open Notebook](https://github.com/lfnovo/open-notebook)：Notebook、Source、Note、独立聊天会话和显式上下文控制。
4. [ScholarPhi / Scholar Reader](https://github.com/allenai/scholarphi)：把论文实体与 PDF 页面坐标连接到交互式阅读器。
5. [SkimRead for Zotero](https://github.com/adellife/zotero-skimread)：利用章节结构提取核心叙事、排除参考文献、按章节处理长文档，并将临时结果与正式批注分开。
6. [Zotero Research Copilot](https://github.com/OneOneLiu/Zotero-Research-Copilot)：明确分开“当前论文阅读器对话”“文库助手”和“用户选择范围的多论文分析”。

## 各项目的成熟做法

### Docling：先得到结构化文档，再做检索

Docling 的统一文档对象不只保存纯文本，还保存标题、段落、表格、图片、父子层级、阅读顺序、页面坐标和来源信息。它优先使用 PDF 自带书签确定标题层级，再用布局信号补充。这说明“章节是什么”应来自结构解析结果，而不是从 Top-k 文本片段猜测。

### PaperQA2：证据收集不是一次向量搜索

PaperQA2 将流程拆成论文搜索、证据收集和回答生成。证据收集会先召回文本块，再围绕当前问题为每个文本块生成带相关度的摘要并重新筛选；代理还可以使用不同措辞做宽搜索与窄搜索。这说明内容型问题可以继续使用 RAG，但需要问题改写、覆盖检查和二次重排，不能把任意五段直接交给模型。

### Open Notebook：资料范围和会话必须显式

Open Notebook 使用 Notebook 组织 Sources 和 Notes，支持一个 Notebook 中的多个聊天会话，并允许用户精细控制提供给模型的上下文。这说明“资料归属”和“会话归属”应是独立的一等数据，而不是只在页面状态中临时存在。

### ScholarPhi：解释必须能回到页面位置

ScholarPhi 的 API 和处理管线将论文实体与边界框关联，阅读器由此在原始 PDF 上提供交互。对本项目而言，目录标题、公式、术语和引用最终都应保存页码及坐标，才能让用户点击后回到原文，而不是只显示一段脱离页面的文本。

### SkimRead：帮助阅读，而不是替代阅读

SkimRead 根据完整文档和章节边界选择核心叙事，排除参考文献；长文档按章节边界分批处理。结果默认只是临时高亮，只有用户明确操作才转为正式批注。这与本项目的人工确认原则一致，也说明推荐问题和阅读路线应根据论文结构生成，而不是所有论文共用一套按钮。

### Zotero Research Copilot：单篇、文库、多篇是三种模式

该项目将当前 PDF 对话、文库助手和用户选择论文后的多篇分析分成独立入口。多篇分析先确定选中文献范围，再逐篇抽取、最后综合。这个范围设计可以防止不同论文的证据与历史在用户不知情时混合。

## 对 ResearchCopilot 的取舍

| 决策 | 借鉴来源 | 本项目做法 |
|---|---|---|
| 建立结构化论文对象 | Docling | 保存标题层级、段落、类型、页码、坐标和父级章节；简单 PDF 走快速解析，异常 PDF 再升级解析器。 |
| 问题意图路由 | Docling、PaperQA2 | 先区分元数据、全文结构、当前选区、内容检索和跨论文问题，再选择不同工具。 |
| 章节感知检索 | Docling、SkimRead | 文本块继承章节路径；章节问题优先在对应章节内检索，参考文献默认排除。 |
| 问题改写和证据覆盖 | PaperQA2 | 对内容问题生成宽/窄检索词，合并候选、重排，并显示证据是否覆盖回答所需范围。 |
| 每篇论文独立会话 | Open Notebook | `paper_id` 下建立多个命名会话；默认只使用当前会话和当前论文。 |
| 明确范围模式 | Zotero Research Copilot | 页面显示“当前论文 / 选定论文 / 文库”范围；第一版只开放当前论文，后两种必须由用户主动选择。 |
| 动态阅读路线 | SkimRead | 根据论文类型和章节结构生成推荐问题，保留“核心叙事/补充证据”的层次。 |
| 页内定位 | ScholarPhi | M7 保存标题和文本块坐标，为目录跳转与后续高亮提供依据。 |

明确拒绝：

- 不让模型仅根据局部 Top-k 证据回答全文统计问题。
- 不自动把其他论文或整个文库加入当前问题的上下文。
- 不把 AI 生成的高亮、总结或阅读路线直接写入正式笔记。
- 不在 Mac 第一版中默认启用重量级 OCR/布局模型；先做质量检测，再按需升级。

## 数据与隐私边界

- 结构解析、目录、章节统计和问题路由默认在本地完成。
- 当前论文内容问答只发送问题和经过本地筛选的证据。
- 当前选区问题发送选区及必要的局部上下文，并在页面明确展示范围。
- 跨论文问题必须由用户明确选择论文集合，不能根据历史自动扩大范围。

## 实现顺序

1. 建立 `PaperDocument` 结构和解析质量报告。
2. 提取 PDF 自带目录；没有目录时使用编号、字体和布局信号推断标题层级。
3. 在页面增加可点击目录，并将标题绑定真实 PDF 页码。
4. 增加确定性问题路由：元数据、结构、选区、内容检索、暂不支持的跨论文范围。
5. 让文本块携带章节路径，增加章节过滤和参考文献排除。
6. 为当前论文生成独立阅读路线与推荐问题。
7. 将每篇论文的问答拆成可命名的独立会话。

## 验收标准

1. 对带 PDF 书签的真实论文，目录标题、层级和页码正确。
2. 对无书签但标题编号清晰的论文，能识别主要章节，并标记推断置信度。
3. “这篇论文有多少页/章节”不调用普通 Top-k RAG。
4. “解释 3.2.1 节”优先检索该章节，并保留章节路径和 PDF 页码。
5. 切换论文后，推荐问题、会话、历史和卡片都只显示当前论文的数据。
6. 新建两个会话后，两个会话的消息不互相出现。
7. 对无法可靠识别结构的 PDF，页面显示解析警告，不伪造目录。
8. 至少使用三篇版式不同的真实 AI 论文完成验收。

## 暂不实现的内容

- 默认跨整个文库自动回答。
- Windows/CUDA 复现实验编排。
- 对所有扫描 PDF 自动运行 OCR。
- 自动把临时阅读路线或高亮写入正式 Markdown。
