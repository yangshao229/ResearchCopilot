# M6.5.5 原文语言与界面语言：开源论文阅读产品拆解

检索日期：2026-09-27。只借鉴产品思想，不复制第三方代码。

## 用户问题

英文论文、中文论文和中英混排 PDF 都可能进入资料库。当前产品保存了回答语言和译文目标，却没有说明 PDF 的原文语言；如果把界面语言等同于原文或译文语言，切换界面就可能意外改变模型请求、术语和缓存。用户需要看懂这几个设置各自影响什么，也需要在自动判断错误时纠正。

这些项目说明**四个维度必须分离**：界面语言（按钮文案）、原文语言（PDF 文本属性）、回答语言（问答输出）、翻译目标（译文输出）。术语表还需要与翻译目标绑定。它们没有提供可直接套用到本项目 PDF 的可靠自动语言检测算法，因此本阶段采用透明的本地启发式，并公开“不确定”。

## 对 ResearchCopilot 的取舍

| 决策 | 理由 |
| --- | --- |
| 原文语言来自少量可抽取 PDF 正文的本地估计，允许 `en`、`zh-CN`、`mixed`、`unknown` | 不上传 PDF、不下载检测模型；扫描件、公式页和多语言论文不能假装确定。 |
| 用户可按论文覆写为英文或中文，也可恢复自动判断 | 语言判断是阅读辅助，不应替代人工判断。覆写复用既有论文级语言偏好存储，不新建事实数据库。 |
| 原文语言只展示和提示，不自动修改回答语言、译文目标、检索或证据 | 避免自动检测错误引发连锁行为；原文与译文仍由现有选区/页码锚点隔离。 |
| 界面语言属于整个浏览器使用者，不属于论文 | 下一内部步骤以独立前端消息表和本地偏好实现，不放进论文的 `LanguagePolicy`，不发送给模型。必须覆盖完整用户可见界面后才标记完成。 |
| 本步不加入大模型语言检测 | 会上传论文样本、增加费用和不稳定性；对中文/英文读论文最小版本不必要。 |

## 架构影响与兼容性矩阵

`PaperSummary` 增加本地检测结果；`LanguagePolicy` 仅增加用户的 `source_language_override`。检测结果不保存在阅读记录里，也不改变原有 `ReadingContext` 的问答参数；覆写仍随该论文的语言偏好持久化。界面语言将来是浏览器级 UI 状态，不能塞进 `ReadingContext`。PDF 原文、搜索索引、页码与论文卡片不修改。

| 情况 | 预期 |
| --- | --- |
| 当前论文/另一论文 | 检测针对各 PDF；覆写按论文 ID 隔离。 |
| 原文/译文 | 识别只读原文；译文和术语仍按现有目标语言规则处理。 |
| 同一论文不同会话 | 共用该论文的原文语言覆写；会话记录继续独立。 |
| 本地/云端 | 检测和覆写完全本地；只有用户主动提问/翻译时才走现有模型流程。 |
| macOS/Windows | 标准库与现有 `pypdf`，无新模型或系统依赖。 |
| 扫描、空白、混排、检测错误 | 返回 `unknown`/`mixed`，或由用户手动纠正；不阻止阅读。 |

## 实现顺序与验收标准

1. 写纯函数按有限 PDF 文本判断英文、中文、混合或未知，测试公式/扫描件与中英混排。
2. 论文列表暴露自动结果；论文语言设置增加用户覆写并保留旧 JSON 兼容。
3. 阅读页面明确显示“自动判断/手动指定”，修改只影响当前论文；保留回答语言与翻译目标独立设置。
4. 自动测试和真实 PDF 验收；不需要真实 DeepSeek。下一阶段完成整站中英界面消息表和切换，不做半套 UI。

暂不实现第三种原文语言、OCR、自动改译文目标、整篇双语重排或系统级语言检测服务。
