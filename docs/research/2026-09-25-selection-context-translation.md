# M6.5.2 选区上下文翻译：开源产品拆解

检索日期：2026-09-25

## 用户问题

当前阅读器把用户划选的文字作为一段指令拼进普通问答，然后仍由全文检索决定实际证据。这样会有两个问题：被选中的原句不一定进入模型证据；短句离开上下文后也可能误译。用户还看不到请求究竟会发送选区本身、所在段落还是整页内容。

本步只解决：**为当前 PDF 页中的选区恢复有限的原文上下文；请求前显示实际将发送的文本范围；翻译仍关联当前论文、会话、页码和目标语言，并走既有阅读记录链。** 不实现整篇双语文档、跨页版面重建、术语库和缓存。

## 参考项目与一手资料

1. **Zotero Context Translate**：官方仓库/README 描述按 PDF 文本层恢复选区所在句与段，段落任务再带邻近段落；请求前由用户明确触发，选区和上下文发给用户配置的 LLM，整篇转换与局部翻译分开。AGPL-3.0-or-later。<https://github.com/maverickzyc/zotero-context-translate>
2. **Marginalia**：官方仓库 README 采用“选中后在侧栏发起翻译/解释”，并把精确选区、周边段落、章节/整书摘要做成可查看和切换的上下文片段；每本书独立保存会话。GPL-3.0-or-later。<https://github.com/EurFelux/marginalia>
3. **PaperQuay**：官方仓库强调原 PDF、解析块、译文、批注与概览保持关联；解析块级译文缓存，阅读时跳转到对应原文，而不是仅保留被替换后的译文。AGPL-3.0。<https://github.com/WangQrkkk/PaperQuay>
4. **Zotero PDF Translate**：成熟的选区弹窗翻译可手动触发、保留原文并允许添加到笔记；它提供更多传统翻译引擎，但不主打恢复长段落上下文。AGPL-3.0。<https://github.com/gouqi7/Zotero-PDF-Translate>

核心实现依据均为项目官方 README/仓库说明；本步只借鉴交互与数据流，不复制代码或引入其许可证下的代码依赖。

## 各项目的成熟做法

| 项目 | 交互与证据范围 | 可借鉴点 | 不适合直接照搬之处 |
| --- | --- | --- | --- |
| Zotero Context Translate | 用户选区触发；恢复句/段及有限邻段；显示词典与翻译两个不同任务 | 短选区需要原段语境；翻译明确用上下文 | 当前第一步不需整篇翻译管线、词典、流式 UI、术语库或新历史数据库 |
| Marginalia | 选择文字后动作在侧栏完成；各类上下文以可见片段呈现、可开关 | 明示“模型看到什么”，用户能检查上下文范围 | 整书摘要记忆超出单篇原文选区翻译的最小范围 |
| PaperQuay | PDF 与结构块、译文及笔记始终关联；预先解析的块可缓存 | 不替换原文，结果始终回到原文块 | MinerU 预解析、批量翻译和桌面端存储迁移成本较高，当前不引入 |
| Zotero PDF Translate | 用户手动触发翻译，结果可复制/写入注释，目标语言可配置 | 明确触发 API，保留原文 | 只送选区会损失学术句法、术语与代词指代信息 |

## 对 ResearchCopilot 的取舍

| 决策 | 设计 |
| --- | --- |
| 采用 | 由用户显式点“翻译”才发起云端请求；先展示选区与恢复出的上下文，再允许发送。 |
| 采用 | 优先从同一 PDF 页的已解析文本中定位选区；恢复所在段落，选区很短/段落边界不可靠时限制邻域，不发送整页或整篇。 |
| 采用 | 保留精确选区与上下文的区分；提示目标语言、论文、页码及即将发送的字符/文本。 |
| 调整 | 用户选中的原文是翻译任务的直接证据，不能只依赖 top-k RAG 是否碰巧检索到它；需要时可附少量检索证据，但原文上下文和检索补充必须在 UI/记录中可区分。 |
| 采用 | 将 `task=translate`、现有 `ReadingAnchor`、`LanguagePolicy` 和 `ReadingRecord` 衔接起来；不新增第九类核心对象、平行会话或独立聊天流水线。 |
| 拒绝 | 不覆盖 PDF 原文，不把译文写入证据索引，不把普通问题提示词伪装成一条专用翻译记录。 |
| 拒绝 | 不在 M6.5.2 加整篇翻译、并行双栏、跨页版面解析、离线词典、术语库管理、自动翻译或缓存；分别等解析/用户反馈后决定。 |

## 架构与数据边界

- 复用 `ReadingContext.task`、`ReadingContext.anchor`、`LanguagePolicy`、`Evidence`、`ReadingRecord`、论文会话和本地 JSON 历史。
- 选区页码是原文锚点。恢复上下文只能从该 PDF 页取得，不能因全文检索命中其他页而替代所选页。
- 服务端在本地从既有分页抽取结果读取所在页，并恢复上下文；不上传整篇 PDF，也不新增外部解析服务。
- DeepSeek 请求只包含精确选区、有限恢复上下文、目标语言/术语策略，以及 UI 明示的必要检索补充。
- 完整发往云端的上下文范围在点击前可检查；翻译记录保留任务、论文/会话、锚点和语言策略快照。模型输出仍是未确认草稿。
- 当前 PDF 文本层无法唯一匹配选区、选区跨页或上下文边界不可靠时，不猜段落：安全回退为精确选区，并在发送预览中明确提示“未恢复段落上下文”。
- 本机解析文本与记录保留在本地；仅用户确认的翻译请求将最小必要文本发送给配置的 DeepSeek API。API 密钥不进入记录。

## 兼容性检查

| 维度 | 验收行为 |
| --- | --- |
| 当前论文 / 切换论文 | 锚点只能属于当前论文；切换后不可复用旧论文选区。 |
| 原文 / 译文 | 始终同时可查看原选区与译文；译文不替代原文证据或污染检索。 |
| 不同会话 | 请求与阅读记录归当前会话；已有旧记录缺字段时可读取。 |
| 本地 / 云端 | 段落定位本地完成；仅显式发送后将预览范围发送至 DeepSeek。 |
| macOS / Windows | 使用跨平台 Python/JSON 与浏览器 API，不依赖系统特有路径或 PDF 应用。 |

## 验收标准

1. 对页内可定位的短选区，恢复文本包含原选区且限制在同页合理段落范围内。
2. 非唯一/不可定位或跨页选区安全回退为精确选区，不错误拼接别页内容。
3. “翻译”请求携带 `task=translate`、目标语言、论文 ID、会话 ID、页码锚点与所选原文；旧版只发送 query 的问答请求仍兼容。
4. 用户请求前能看到精确选区、恢复上下文及实际发送范围；取消/关闭预览不会产生 API 调用或阅读记录。
5. 翻译回答按目标语言生成，记录任务与锚点；仍显示原文引用页码，不把翻译文本当作论文证据。
6. 论文偏好切换、原文/译文差异、多个会话隔离和后端模型失败场景均有自动测试。
7. 真实 PDF 手工验收：至少一个选区命中段落、一个无法定位回退案例；不要求 Hugging Face 在线或调用真实 API 才可跑自动测试。

## 实施顺序与暂不实现

1. 先写页内选区上下文恢复的纯函数与失败回退测试。
2. 将任务与锚点从前端请求传到现有统一阅读上下文，并把直接原文片段作为翻译的确定性证据。
3. 在侧栏加入预览/发送范围说明，并复用当前语言偏好和会话。
4. 更新验收与学习地图，验证旧问答、普通选区解释和论文卡片流程无回归。

暂不实现段落缓存、用户维护术语表、原文语言自动检测、整篇/章节双语视图及复杂版面跨页重建。当前逐页纯文本只能支持保守段落边界；更可靠的多栏/公式/表格结构恢复属于 M7，不在此处堆叠解析器。
